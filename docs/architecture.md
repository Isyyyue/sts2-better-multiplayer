# 架构说明

## ADR-001：复用 Steam 官方大厅与中继

状态：已采用

二代原生 `SteamHost` 使用 Steam Lobby 和 `SteamNetworkingSockets`。本 Mod 只把自己创建的大厅从好友可见改为公开，并增加可搜索元数据；数据传输仍走 Steam Datagram Relay。这样无需自建服务器、端口映射或第三方内网穿透。

## ADR-002：密码证明不保存明文

状态：已采用

房主创建房间时生成随机盐，并用 PBKDF2-SHA256 派生密钥。大厅公开盐和固定挑战的 HMAC 校验值，使客户端可以在连接前确认房间名称与密码同时匹配；加入后再通过 Steam Lobby member data 提交绑定大厅 ID 与 Steam ID 的 HMAC 证明。所有比较均使用常量时间；密码和派生密钥不会写入大厅或日志。

该方案用于休闲游戏房间访问控制，不等同于高价值账户认证。大厅校验数据可被观察，因此弱密码仍可能被离线猜测。

## ADR-003：房主程序自动结算交易

状态：已采用

交易请求、报价、确认和取消先到房主程序，但房主玩家不需要额外点击批准。房主程序校验双方库存、数量上限、药水槽、重复遗物和禁交易物品；只有交易双方确认同一修订号后，才自动广播唯一事务。所有节点按同一事务应用，已处理的事务号会被忽略。

篝火事务只允许卡牌、遗物和药水，每名玩家在同一个篝火最多成功交易一次；交易选项返回后仍可正常选择休息或锻造。商店事务只允许金币，成功后保留双方的交易可用状态，因此可在同一家商店连续交易。

## ADR-004：协助锻造由房主校验选择结果

状态：已采用

发起者使用官方队友目标选择和官方锻造牌组界面完成选择。最终选择发送给房主程序，房主校验目标玩家、牌组序号、卡牌 ID、升级等级与当前可升级状态，再向所有节点广播同一结果。若选择期间队友牌组发生变化，本次操作失败并返回篝火界面，不消耗发起者的篝火行动。成功后所有节点执行同一张牌的官方升级命令与锻造 Hook，并由官方篝火同步器消耗发起者的行动。

## ADR-005：暂不实现自动重连

状态：已采用

游戏 `0.107.1` 已有 `ClientRejoinResponseMessage` 和完整战斗快照，但正式加入界面会拒绝进入正在进行的对局，调试客户端的恢复分支也仍直接抛出 `NotImplementedException`。实现它需要补齐场景、战斗队列、UI 和同步器恢复，不属于低风险改动。

房主掉线时沿用原版流程：所有人退出，由房主重新创建房间并加载官方存档。本 Mod 不在交易后调用 `SaveRun`，因此恢复点严格遵循原版规则：尚未进入下一房间时回到上一房间结束状态，已经进入下一房间时回到刚进入该房间的状态。

## ADR-006：诊断反馈采用一次性白名单 Envelope

状态：已采用

玩家主动点击“发送反馈”后，Mod 从固定类型的内存环形记录中生成一个不超过 64 KiB 的 Sentry Envelope。环形记录最多保存本次游戏进程中的 48 条，上传时只保留最近 3 天；记录只接受枚举、数值、布尔值和经过验证的版本、哈希与节点分类，不读取原始日志、存档、截图、房间凭据、房间人数、网络类型、Steam 身份、机器名、环境变量或任意玩家文本。事件设置 `infer_ip=never`，不添加 `user`、`request` 或 `server_name` 字段，也不创建磁盘离线队列。

上传器直接使用项目的公开 DSN 接收端点，不初始化或修改游戏自带的全局 Sentry SDK，避免干扰 MegaCrit 自己的错误上报。只有传输层收到 `2xx` 才报告提交成功；连接错误最多以同一事件号重试一次，HTTP 错误不自动重试，`429` 会遵守 Sentry 的冷却响应。
